# 快照按文件名分组，并用"文档标识"把文件与版本目录对齐

_Status: accepted_

快照曾经按"路径哈希"分目录，目录名是一串十六进制，人工完全认不出、也不好维护。改成**每个源文件一个同名目录**（`versions\test.docx\`），并在两处持久化一个**文档标识**：快照根目录的 `documents.json`（汇总所有文档）与该文档目录内的 `index.json`。

对齐规则（按优先级）：
1. **先按路径查汇总表**——命中就沿用，日常编辑/打开/保存都不会被误判成新文件；
2. 路径查不到时，再用**内容哈希**去汇总表里找：
   - 命中且记录的**原路径已不存在** → 判定**改名/移动** → 沿用原标识，并把目录同步改名；
   - 命中但原路径**还在** → 判定**副本（另存为/资源管理器复制）** → 算新文件；
   - 没命中 → 新文件。

## Consequences

**为什么必须有第 2 步里"原路径是否还在"这一个判据**：副本的字节和原文件完全相同，任何从内容算出的哈希都必然相同。改名与副本之间**唯一**可判别的差异就是"原路径还在不在"。所以"只看哈希"无法同时满足"改名接上"和"副本算新文件"。

**无法区分的一种情况**（已知取舍）：同一个路径上的文件被**整体替换**成另一个文档，与"该文件在别处编辑过再放回原路径"在磁盘上不可区分。本方案按路径认作同一文档、沿用历史。

**两条硬约束**（都踩过）：
- **不要用 `SaveCopyAs`**：Word 的 `Document` 没有可用的 `SaveCopyAs`（那是 Excel / PowerPoint 才有的），调用会抛"Failed to process method"。
- **读取宿主正在使用的文件必须用宽松共享**：Word/Excel/PPT 持有目标文件的**写**句柄，用默认的 `FileShare.Read` 会直接撞共享冲突（表现为"另一个程序正在使用此文件"）。快照库一律用 `FileShare.ReadWrite | FileShare.Delete` 打开。
